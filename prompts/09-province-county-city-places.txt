# PLANRO — PROVINCE + COUNTY(+PLACES) + CITY(+PLACES)
# پرامپت خودکفا — همهٔ دستورات داخل همین فایل است

بعد از دریافت این پرامپت، Agent باید خودش MCP را آماده کند و سپس **کل استان** را یک‌سره جمع‌آوری کند:
**استان + همهٔ شهرستان‌ها به‌همراه Placeها + همهٔ شهرها به‌همراه Placeها**
(روستا پیش‌نیاز DFS است و باید کامل شود — بخش ۵).

فقط یک ورودی: `province_id`. Scope جدا از کاربر نخواه. سؤال تعاملی نپرس.

---

## 0) RUN VARIABLES
```text
province_id=<PROVINCE_ID>
```
قرارداد ورودی Runtime (authoritative):
- اگر در Task مقدار واقعی آمده باشد (`province_id=30` یا فقط `30`) همان authoritative است؛ placeholder را نادیده بگیر.
- نبود مقدار واقعی → فقط `MISSING_INPUT: province_id` بده و متوقف شو.
- عدد مثل `1` را به `province-{n}` normalize کن (MCP هم همین کار را می‌کند؛ هر دو شکل OK).
- هرگز `scope_id`، نام استان/شهرستان/شهر، یا مسیر فایل از کاربر نخواه.

## 1) MCP bootstrap — اجباری قبل از هر تحقیق
قبل از هر تحقیق، workspace را بررسی کن. اگر clone معتبر پروژه موجود نیست، خودت اجرا کن:

```bash
git clone https://github.com/alireza2000sajedi/data-json-mcp.git
```

سپس داخل clone:

```bash
npm install
npm run build
npm run verify
```

بررسی اتصال MCP:

```bash
node mcp-client.mjs list-tools
node mcp-client.mjs list-resources
```

قواعد:
- فایل‌ها و Resourceهای واقعی را از همان clone/workspace بخوان.
- اگر MCP متصل نیست، مشکل فنی bootstrap را بررسی کن؛ فقط در صورت غیرقابل‌اجرا بودن با `MCP_UNAVAILABLE` متوقف شو.
- نبود فایل/Resource را قبل از تلاش برای clone گزارش نکن و از کاربر فایل نخواه.
- هرگز `output/` را به `.gitignore` برنگردان.

## 3) هدف این ران (دامنهٔ قطعی)

### داخل محدوده — باید کامل شود
| لایه | Entity اداری | Place / Camping |
|---|---|---|
| **استان** | `province.json` کامل | Place مستقیم استان (`provincePlaces`) + camping سطح استان |
| **شهرستان** | هر `county-*/county.json` کامل | Place مستقیم شهرستان (`countyPlaces`) + camping سطح شهرستان |
| **شهر** | هر `city-*/city.json` کامل | Place شهر (`places`) + camping سطح شهر |
| **روستا** | هر `village-*` کامل (پیش‌نیاز DFS) | Place / Camping زیر همان روستا |

«کامل» = schema معتبر + ۵ Primary ثبت‌شده (`satisfied:true`) + Visit مجاز همان نوع + FAQ مستقل + travelChecklist مستقل + Media به target + متن انسانی بدون OTA + مختصات قابل‌اتکا + discovery trackهای مربوط با count واقعی بسته شده.

### مسیر خروجی
```text
output/{province_id}/
├── province.json
├── place-*.json                          ← Place مستقیم استان
├── county-{p}-{n}/
│   ├── county.json
│   ├── place-*.json                      ← Place مستقیم شهرستان
│   ├── city-{p}-{m}/
│   │   ├── city.json
│   │   ├── place-*.json                  ← Place شهر
│   │   └── village-{p}-v{k}/…
│   └── village-{p}-v{k}/…
```

### خارج از این ران
- پاس بازنویسی سراسری متن (`06`) — ولی متن save اول باید از همین حالا انسانی باشد (بخش ۱۲)
- audit/minify نهایی (`05`)
- media-gap جدا (`08`) — اینجا media را از همان ابتدا به target برسان؛ به `08` موکول نکن

## 4) قفل Scope — کل استان یک‌سره (برخلاف پرامپت ۰۱)
در پرامپت ۰۱ بعد از Province متوقف می‌شوی. **اینجا متوقف نشو.**

1. `import_province_scopes(provinceId)` — یک بار؛ idempotent؛ درخت County/City/Village را از `input/{n}.json` می‌سازد.
2. بلافاصله `set_active_scope({ provinceId, nodeId: provinceId })` بزن → حالت continuous whole-province.
3. وقتی `awaitingScopeSelection=true` شد، **نایست** و از کاربر Scope نپرس؛ با همان `set_active_scope(provinceId)` کل استان را باز کن.
4. صف کار: `list_pending_nodes({ provinceId, allScopes: true })` و `get_next_research_node`.
5. ترتیب DFS را خودت حدس نزن؛ فقط از MCP بگیر.

---

## 5) روستا — قانون بدون‌خطا (اجباری)
ترتیب DFS زیر هر شهرستان در قرارداد MCP:

```text
district → ruralDistrict → city → village → countyPlaces → camping
```

**Place سطح شهرستان تا وقتی روستاهای همان شهرستان بسته نشوند در صف نمی‌آید.**
`import_province_scopes` روستاها را ثبت می‌کند. حذف/رد/رد شدن از روستا برای سرعت ممنوع است.

برای هر `village-*`:
1. Entity روستا را کامل کن (media target ۳؛ openingHours برای خود روستا ممنوع).
2. Place / Camping زیر روستا را کشف و کامل کن.
3. `complete_discovery_task` برای `places` و `camping` با count واقعی.

---

## 6) SPEED MODE — سرعت بدون خراب‌کردن داده
هدف: سریع‌تر تمام کن، نه ساده‌تر.

اجازه داری:
- جستجوهای یک Entity را موازی کن (۵ Primary + مختصات/نقشه + media wave)
- از `discover_subtree` برای صف Queryها استفاده کن
- Queryهای فارسی/انگلیسی/نام جایگزین را هم‌زمان بزن
- Source Matrix / وضعیت notes را بخوان تا دوباره‌کاری نکنی
- متن را از همان save اول انسانی، Factمحور و بدون نام OTA بنویس

اجازه نداری:
- حذف/رد Village، Place، Source، تصویر، یا Cross-check برای «زودتر تمام شدن»
- کم‌کردن Coverage پنج Primary یا media target
- چند `save_active_entity` هم‌زمان روی Nodeهای مختلف
- commit وقتی `complete:false` یا `invalid>0`
- id جعلی taxonomy داخل Entity؛ staging فقط در `taxonomy/agent-taxonomy/`

ترتیب امن: تحقیق موازی → یک save خطی از MCP → حلقه تا pending صفر → DoD/validate → git.

## 7) تعریف نوع Entity و کاربرد فیلدها
ماتریس قطعی: `planro://rules/entity-fields`. خلاصهٔ اجباری:

### Province
- Visit فقط: `bestSeasons`, `bestMonths`
- ممنوع: openingHours، entryFee، difficulty، guide، reservation، duration، bestTimeOfDay، crowdLevel
- FAQ / Checklist / Media / Safety / Transportation فقط سطح خود استان
- عکس باید نمایندهٔ خود استان باشد، نه صرفاً یک Place معروف داخل آن

### County
- Visit فقط: `bestSeasons`, `bestMonths`
- FAQ/Checklist/Media/Transportation متعلق به خود County؛ child-specific ممنوع

### City
- Visit: `bestSeasons`, `bestMonths` + `crowdLevel` فقط با منبع معتبر
- openingHours و entryFee و مشخصات عملیاتی Placeهای داخل شهر ممنوع

### Village
- Visit می‌تواند: duration، bestTimeOfDay، bestSeasons، bestMonths، entryFee، difficulty، reservation، guide، crowdLevel
- openingHours برای خود Village ممنوع

### Place
- Visit کامل: duration، bestTimeOfDay، bestSeasons، bestMonths، openingHours، entryFee، difficulty، reservation، guide، crowd
- FAQ/Checklist/Media فقط برای همین Place

### Camping
- Visit و Checklist و FAQ و Media مخصوص همان محل کمپینگ

### Costs — حذف‌شده
فیلد `costs` و مدل CPI حذف شده‌اند. قیمت حدس نزن و وارد Entity نکن.

### Ownership
Parent می‌تواند در content به Child در سطح معرفی اشاره کند، ولی operational data را duplicate نکن:
- child ticket / opening hours / facilities / directions / FAQ / checklist
این‌ها فقط روی Child ذخیره می‌شوند.

## 9) Checklist model
`travelChecklist` برای هر Entity مستقل است.
حالت‌ها: `tour` / `personalCar` / `airplane` / `camping` / `train` / `bus`.
آیتم‌ها فقط canonical id از `planro://taxonomy` / `taxonomy/checklist-items.json` (مثل `tent`, `sunscreen`, `snow_chains`).
متن آزاد فارسی، جمله، مسیر، قیمت یا توصیه داخل checklist ممنوع.
کپی کامل Checklist از Parent/Child ممنوع.

## 10) Media model
| نوع | target (URL یکتا؛ thumbnail داخل بودجه) |
|---|---|
| Province / County / City / Place | **۵** |
| Village / Camping | **۳** |

قواعد سخت:
- یک image URL بین دو Entity تکرار نشود.
- عکس Parent/Child/Sibling برای Entity دیگر قابل استفاده نیست.
- چند جستجوی مستقل؛ از ۱–۲ عکس متوقف نشو.
- منابع media: Wikimedia Commons، سایت رسمی، خبرگزاری، مجلهٔ گردشگری معتبر، گالری عمومی، صفحات مقصد — محدود به ۵ Primary نباش.
- هر عکس: `record_media_candidate` با `imageUrl` مستقیم فایل HTTPS + `pageUrl` + license/credit معتبر (`all-rights-reserved` با credit مجاز است).
- سپس `finalize_media(nodeId)` → به Entity بچسبان → `save_active_entity`.
- `mark_node_media_deficit` فقط وقتی **هیچ دادهٔ Entity قابل ذخیره نیست**. کمبود عکس به‌تنهایی deficit نیست؛ اگر JSON داری و عکس کم است، media را partial/complete بساز نه deficit.

## 11) Sources
پنج Primary (به ترتیب priority در Source Policy):
1. kojaro.com
2. jabama.com
3. alibaba.ir
4. lastsecond.ir
5. flytoday.ir

برای **هر** Node از نوع Entity:
- هر پنج منبع را واقعاً جست‌وجو کن.
- با `record_search_result` ثبت کن؛ no-result (`resultCount=0`) و unreachable هم باید ثبت شود.
- تا `get_source_coverage(nodeId)` → `satisfied:true` نشده، Entity ننویس.
- Media discovery جای Fact Source Coverage نیست.
- فیلد `evidence` حذف شده؛ Factها در `sources[]` و متن Entity.
- در متن کاربرمحور: نام پلتفرم Primary، امتیاز ستاره‌ای، تعداد رزرو، «طبق سامانهٔ…» ممنوع. فقط در `sources[]` (URL لازم؛ title را می‌توان خنثی کرد).
- متن کاربر نباید شامل query، search engine، یادداشت تحقیق، یا فرآیند جمع‌آوری باشد.

Fallback فقط برای cross-check/تکمیل (جایگزین Primary نیست): Wikipedia، Wikidata، OSM، Iranica، gov.ir و …

## 12) Taxonomy
همه type / subType / category / activity / feature / facility / risk / checklist item در Entity فقط از Global Taxonomy (`planro://taxonomy`).

اگر مفهوم reusable در Global نبود:
1. تحقیق کن و آیتم کامل taxonomy بساز.
2. در کاتالوگ متناظر زیر `taxonomy/agent-taxonomy/` بنویس (`types` / `subtypes` / `categories` / `activities` / `features` / `facilities` / `risks` / `checklist-items`) با `id` + `label` (+ `appliesTo`/`group` اگر لازم) و `source` (provinceId، nodeId، reason، proposedAt، urls).
3. آن id را هنوز وارد Entity نکن؛ تا promote انسانی فقط staging است (`planro://taxonomy/agent`).
4. در گزارش پایان ران بگو چه idهایی staging شد و در کدام فایل کاتالوگ.
Taxonomy داخل Province کپی نشود.

## 13) کیفیت متن — انسانی بنویس؛ ردپای AI و OTA ممنوع
مرجع لحن: `planro://rules/brand-voice-guide`. از همان save اول الزامی است.

### ۱۳-۱ خروجی هدف
مثل نوشتهٔ یک ادیتور انسانیِ گردشگریِ فارسی بنویس. خواننده نباید حس کند متن با مدل زبانی، ویکی‌ربات یا کاتالوگ رزرو ساخته شده.
در گزارش/commit ننویس که متن «با AI» نوشته شده.

### ۱۳-۲ از نو بنویس، کپی نکن
- جملهٔ منبع را نچسبان؛ paraphrase مکانیکی ممنوع.
- Fact فقط از منابع ثبت‌شدهٔ همان Node؛ عدد/تاریخ/قانون اختراع نکن.
- اگر Fact از OTA آمد، به زبان خنثی و بدون نام پلتفرم بنویس.

### ۱۳-۳ ضد اثر متن ماشینی
ممنوع:
- شروع کلیشه‌ای: «در قلب…»، «واقع در…»، «شایان ذکر است»، «لازم به ذکر است»، «در مجموع می‌توان گفت»
- جمله‌های هم‌اندازهٔ پشت‌سرهم و پاراگراف متقارنِ بروشوری
- ترجمهٔ انگلیسی‌زده: «ارائه می‌دهد»، «فراهم می‌کند»، «امکان تجربه را می‌دهد»
- صفت توخالی: منحصربه‌فرد، چشم‌نواز، دل‌انگیز، رؤیایی، فوق‌العاده، بی‌نظیر، جادویی، ایده‌آل، بهترین، زیباترین، بهشت گمشده، نگین
- FAQ شبیه چت‌بات («البته!»، «حتماً»)
- قالب یکسان برای دو Entity هم‌نوع با اسم عوض‌شده
- کپی متقابل whyVisit / tips

### ۱۳-۴ بدون نام پلتفرم در متن کاربرمحور
در summary / description / whyVisit / history / culture / seo / faq / tips / warnings / media captions ممنوع:
کجارو، جاباما، علی‌بابا، لست‌سکند، فلای‌تودی و هر OTA دیگر؛ امتیاز ستاره‌ای؛ «۶۳ رزرو»؛ «طبق سامانهٔ…».

### ۱۳-۵ Brand Voice
همراه آگاه، دقیق، مشاهده‌محور؛ بدون اغراق آژانسی. سوپرلتیو، کلیشهٔ گردشگری و نویز تکنولوژی/AI ممنوع.

## 15) قرارداد ترتیب فراخوانی MCP (Call Order) — قرارداد است، نه پیشنهاد

### ۱۵-۱ Bootstrap استان
1. `import_province_scopes(provinceId)`
2. `set_active_scope({ provinceId, nodeId: provinceId })` — continuous whole-province
3. `get_scope_state` / `list_pending_nodes({ provinceId, allScopes: true })`

### ۱۵-۲ حلقه برای هر Node تا `pending:0`
1. `get_next_research_node` یا از صف `list_pending_nodes` — ترتیب را حدس نزن.
2. `get_node_context(nodeId)` — قبل از تحقیق.
3. در صورت واحد اداری: `discover_subtree` برای صف Place/Camping.
4. `record_search_result(...)` برای هر پنج Primary (حتی no-result/unreachable).
5. `get_source_coverage(nodeId)` → باید `satisfied:true`.
6. `record_media_candidate(...)` برای هر عکس → `finalize_media(nodeId)` تا target.
7. `save_active_entity({ provinceId, entity, expectedNodeId })` — **تنها مسیر ذخیره**؛ فایل خام دستی زیر `output/` نساز.
8. `complete_discovery_task({ nodeId, track, count })` — `count` = تعداد واقعی Nodeهای ثبت‌شده؛ بدون count رد می‌شود.
   - province: `provincePlaces`, `camping` (و `counties` اگر باز مانده)
   - county: `countyPlaces`, `camping` (+ tracks ساختاری اگر باز)
   - city / village: `places`, `camping`

نکات ابزار:
- `mark_node_complete` مستقیم وجود ندارد؛ تکمیل از مسیر notes/`update_notes` و وضعیت MCP است.
- `resolve_scope_name` حذف شده؛ نام → id از `planro://scopes/{provinceId}` و `indexByName`.
- id Place: الگوی قطعی `place-{p}-{n}`؛ مسیر ذخیره را MCP تعیین می‌کند.
- `reserve_entity_id` / `find_existing_entity` / `create_candidate` / `resolve_candidate` / `link_entities` را وقتی قرارداد Node ایجاب کرد استفاده کن.

### ۱۵-۳ پایان ران
1. `list_pending_nodes({ provinceId, allScopes: true })` → `pending:0`
2. `check_definition_of_done(provinceId)` → `complete:true`
3. `validate_province(provinceId)` → `invalid:0`
4. اگر پاس نشد → همان Nodeها را تعمیر کن و دوباره ۲ و ۳ را بزن؛ Scope را تکه نکن.

## 19) تحویل (Delivery) — بعد از DoD موفق اجباری
1. گزارش بخش ۱۸
2. `check_definition_of_done` → `complete:true`
3. `validate_province` → `invalid:0`
4. اگر پاس نشد → **commit ممنوع**؛ تعمیر و تکرار
5. پس از پاس:
   - `git status --short output/`
   - `git add output/`
   - commit با پیام واضح برای همین استان (مثلاً `province-30: admin + places complete`)
   - `git push` (شکست push مانع commit محلی نیست، ولی تلاش اجباری است)

اگر متغیر ناقص است فقط `MISSING_INPUT: province_id` بده.
